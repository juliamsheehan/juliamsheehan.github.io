The 5 ways to use AI while coding

Almost everything falls into one of these five modes, ordered from “lightest touch” to “most autonomous.”

⌨️

1 · Autocomplete

Grey “ghost text” finishes your line or block as you type. Press Tab to accept. Zero prompting.

Best for: the next line, boilerplate, repetitive edits.

💬

2 · Chat / ask

A conversation in a sidebar or web app. You describe, it explains or drafts. You copy what's useful.

Best for: “how do I…”, explaining code, brainstorming, small snippets.

🔍

3 · Review & explain

Point it at a diff, a file, or an unfamiliar repo and ask for a review, a summary, or a walkthrough.

Best for: code review, onboarding to a codebase, learning.

✏️

4 · Inline edit

Select code, describe a change (“add error handling”), and it rewrites that selection in place.

Best for: targeted refactors, renames, adding tests to one file.

🤖

5 · Agent

You give a goal; it reads files, makes multi-file changes, runs commands/tests, and fixes its own errors — then reports back.

Best for: whole features, migrations, “make the tests pass.”

🧭

The mindset

Same across all five: you're the pilot, it's the copilot. It drafts fast; you steer, review, and own the result.

Check your knowledgeAcross all five modes, what stays the same?

Autocomplete or full agent, the mindset doesn't change: it drafts fast, but you steer and you own what ships. More power isn't automatically better — match the mode to the task.

Prompting for code (the part that pays off)

The single biggest lever on quality is context — remember from Fundamentals, the model only knows what's in front of it. A vague ask gets a generic answer; a specific ask with context gets a usable one.

The recipe: Goal · Context · Constraints · Format

🔍 Example — before & after

❌ Before: “Write a function to validate email.”

✅ After: “Write a TypeScript function isValidEmail(input: string): boolean for a signup form. Use a simple, readable regex (no external libraries). Trim whitespace first, reject empty strings, and add 3 unit tests including an invalid case. Return just the function and tests.”

Notice the four ingredients: the goal (validate email), the context (signup form, TypeScript), the constraints (no libraries, readable), and the format (function + 3 tests, nothing else).

Habits that consistently work

  • Give it the real code & the real error. Paste them; don't describe from memory.
  • State the stack & versions. “React 18, no Redux,” “Python 3.12,” — it changes the answer.
  • Ask for a plan first on big tasks. “Outline the steps before writing code,” then approve or adjust.
  • Show an example of the style/output you want (few-shot) when the task is fuzzy.
  • Iterate. The first answer is a draft. “Good, now handle timeouts” beats re-writing the whole prompt.
  • Ask it to explain its choices — you learn, and you catch bad assumptions.
✅ Tip

Keep a personal note of prompts that worked well. “Write tests for X including edge cases and error paths” is the kind of reusable recipe that saves you every week.

Show me “iterate” in action

You don't have to nail the whole prompt on the first try — steer with short follow-ups:

  1. You: “Write a function to fetch a user by ID from our API.”
  2. You: “Good. Now handle a 404 by returning null instead of throwing.”
  3. You: “Add a 5-second timeout and one retry.”
  4. You: “Now write two tests: the happy path and the 404 case.”

Each step is tiny and easy to review. That beats writing one giant prompt and hoping — and you can stop the moment it's good enough.

Trust, but verify

AI-generated code can be subtly wrong, out of date, or insecure while looking completely confident. The point isn't to distrust it — it's to have a habit that catches the misses.

  • Run it. The compiler and your tests are honest reviewers that never get tired.
  • Read every line you ship. If you don't understand it, ask it to explain — don't merge mystery code.
  • Check for made-up APIs. Hallucinated function/library names are common; confirm they exist.
  • Mind security. Watch for injected SQL, unvalidated input, hard-coded secrets, or outdated crypto.
  • Small steps. Review changes in reviewable chunks, in version control, so you can undo cleanly.
⚠️ Watch out

You own the code you commit — not the AI. “The assistant wrote it” is never the explanation for a bug in production. Treat its output like a pull request from a fast but junior teammate.

Check your knowledgeAn AI writes a function that calls fetchData() from a library — but you've never heard of that method. What's the right move?

Hallucinated APIs — plausible function or library names that don't exist — are common. Check the real docs, and remember: you own the code you commit, not the AI.

At work vs. personal projects

💼 At your job

  • Check the policy first. Many workplaces have rules about which AI tools are approved and what data may be shared. Follow them before anything here.
  • Don't paste secrets or sensitive data — credentials, customer/PII data, proprietary code — into tools that aren't approved for it. Assume anything you send may be stored.
  • Prefer approved/enterprise tools, which usually promise not to train on your data and keep it in your tenant.
  • Attribute & review per your team's norms; keep changes in code review as usual.

🏠 Personal use

  • Experiment freely. Personal projects are the safest place to try agents and new tools end-to-end.
  • Use it to learn, not just to finish — ask “why,” and read the explanations.
  • Still mind licenses & secrets if you'll publish the repo (no API keys in git!).
  • Build the muscle of writing good prompts and reviewing output — it transfers straight to work.
⚠️ Watch out

This site is general guidance, not your employer's policy. When the two differ, your workplace rules win.

Starter project ideas to practice on

The fastest way to internalize all of this is to build something small with an AI assistant. A few low-stakes ideas, roughly easiest first:

🧰 A personal CLI tool

Automate a chore — rename files, tidy downloads, summarize a folder of notes. Great for practicing the agent loop end-to-end.

🌐 A one-page website

Like this one! Static HTML/CSS/JS on GitHub Pages. Practice inline edits and “explain this” on your own code.

📄 A “chat with my docs” toy

The classic RAG project: point a model at a few of your own PDFs/notes and ask questions. Makes embeddings + retrieval click.

🧪 Add tests to old code

Take a script you already have and ask AI to write a test suite for it. You'll learn testing and verification habits at once.
