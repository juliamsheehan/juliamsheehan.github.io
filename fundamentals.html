AI vs Machine Learning vs LLM

These words get used interchangeably, but they're nested — like Russian dolls.

  • Artificial Intelligence (AI) — the broad goal: machines doing things that seem “smart.”
  • Machine Learning (ML) — a way to get there: instead of hand-writing rules, you show a program lots of examples and it learns the patterns.
  • Deep Learning / Neural Networks — a powerful kind of ML loosely inspired by brain cells, good at messy data like images and language.
  • Large Language Model (LLM) — a very large neural network trained on text. This is what powers ChatGPT, Claude, Gemini, Copilot, and the coding tools you'll use.
💡 In plain English

“AI” is the dream, “machine learning” is the method, and an “LLM” is today's breakout star of that method — specialized in language and code.

How an LLM actually works

An LLM is a next-token predictor. You give it some text, and it repeatedly guesses the most likely next piece of text, adding one piece at a time until it's done.

🔍 Example

Type def add(a, b): into a coding assistant and it predicts return a + b — not because it “understands” math, but because it has seen that pattern countless times.

⚠️ Watch out

Because it's predicting likely text (not fact-checking), it can produce answers that sound perfect but are wrong. That's called a hallucination — always verify.

Check your knowledgeAt its core, what is an LLM doing when it answers you?

An LLM is a next-token predictor. It has no fact database and doesn't run code — which is exactly why it can sound confident and still be wrong.

Tokens

Models don't read whole words — they read tokens, which are word-chunks. A token is roughly ¾ of a word in English (about 4 characters).

  • cat → 1 token
  • unbelievable → often 3 tokens (un · believ · able)
  • Rough rule of thumb: 100 tokens ≈ 75 words.

Common whole words are usually one token; rare or long words get chopped into pieces, and punctuation and spaces count too. That's why word count and token count never line up exactly.

✅ Tip

Tokens matter for two practical reasons: (1) API pricing is usually per token, and (2) every model has a maximum number of tokens it can handle at once — its context window.

Prompts & system prompts

A prompt is simply the text you send the model. Prompt engineering is the craft of wording that text so you get a better answer.

Most chat tools also have a hidden system prompt — a standing instruction set behind the scenes (“You are a helpful coding assistant. Be concise.”) that shapes every reply.

🔍 Example

Weak: “Fix my code.”  →  Strong: “This Python function throws KeyError when the input list is empty. Here's the function and the error. Fix it and explain the one-line change.”

Four ingredients of a strong prompt:

  • Role/goal — what you want and who it's for.
  • Context — the code, error, constraints, versions.
  • Format — “give me a diff,” “bullet list,” “just the function.”
  • Examples — show one input/output pair when the task is fuzzy (called few-shot prompting).

There's a full, coding-specific prompting guide over in Apply to Coding.

Context window

The context window is the model's short-term memory — the maximum amount of text (in tokens) it can consider at one time. Everything has to fit: the system prompt, your conversation so far, any files you pasted, and the room it needs to write the answer.

🔍 Example

Modern models range from ~8,000 tokens (a few files) to 1,000,000+ tokens (an entire codebase or book). Bigger windows let you paste more, but relevant beats big.

⚠️ Watch out

When a chat gets very long, early messages can fall out of the window and the model “forgets” them. Models can also lose focus with too much irrelevant text (“lost in the middle”). Start a fresh chat for a new task, and share only what's relevant.

Check your knowledgeYour chat has gone on for hours and the model seems to have “forgotten” what you said at the start. Why?

Everything has to fit inside the context window at once. In a long chat the oldest text gets pushed out, so it's no longer “in view.” Starting a fresh chat for a new task is the fix.

Temperature (creativity dial)

Since the model picks from ranked next-token options, temperature controls how adventurous that pick is.

  • Low (≈0–0.3) — picks the most likely option almost every time. Focused, repeatable, predictable.
  • High (≈0.8–1.2) — more willing to pick less-likely options. Varied, creative, sometimes off the rails.
If you're generating code, extracting data, or want the same answer twice…
→
Then use a low temperature.
If you're brainstorming names, ideas, or copy variations…
→
Then use a higher temperature. (Most chat apps hide this; it matters most when you call an API.)

Training, fine-tuning & RLHF

How a model gets its abilities — three stages worth knowing by name:

  • Pre-training — the model reads an enormous pile of text/code and learns general patterns. Slow and very expensive; done by the model makers, not you.
  • Fine-tuning — taking that general model and training it a bit more on a narrower set of examples so it specializes (e.g., your company's writing style, a specific format).
  • RLHF (Reinforcement Learning from Human Feedback) — humans rate answers, and the model is nudged toward the helpful, honest, harmless ones. This is what turned raw text-predictors into polite, useful assistants.
✅ Tip

A model's knowledge cutoff is the date its training data stops. Ask about something newer and it either won't know or will guess — unless it can search the web or you give it the info (see RAG).

Hallucination

A hallucination is when the model states something false with total confidence — an invented function that doesn't exist, a made-up citation, a plausible-but-wrong fact.

💡 In plain English

The model is optimized to produce likely-sounding text, not true text. Usually those overlap. When they don't, you get a confident wrong answer. It isn't lying — it has no concept of truth.

How to reduce it:

  • Give it the real source material instead of relying on memory (RAG).
  • Ask it to cite or show its work, then check.
  • For code: run it. Tests and the compiler are your fact-checkers.

Multimodal models

Multimodal means the model handles more than just text — it can also take in (and sometimes produce) images, audio, or video.

🔍 Example

Paste a screenshot of a broken UI and ask “why is this button off-center?”, or hand it a photo of a whiteboard diagram and ask it to turn it into code. That's multimodal input at work.

Embeddings & vectors

An embedding turns a piece of text into a list of numbers (a vector) that captures its meaning. Texts with similar meaning get similar numbers — so you can measure how related two things are by how close their vectors are.

🔍 Example

“How do I reset my password?” and “I forgot my login” land near each other, even though they share almost no words. That's why search built on embeddings (semantic search) beats plain keyword matching.

Embeddings are stored in a vector database, and they're the engine behind the next concept — RAG.

RAG — Retrieval-Augmented Generation

RAG is a pattern for giving a model knowledge it wasn't trained on — your docs, your codebase, last week's news — without retraining it. You retrieve the relevant bits and paste them into the prompt right before the model answers.

💡 In plain English

RAG is an open-book exam. Instead of hoping the model memorized the answer, you hand it the exact page it needs and say “answer using this.” Fewer hallucinations, and it can cite sources.

If you need the model to answer using private or fast-changing information…
→
Then reach for RAG before you consider fine-tuning — it's cheaper, updatable, and easier to trust.

Tool use / function calling

On its own, a model can only produce text. Tool use (a.k.a. function calling) lets it ask your software to do something — run code, search the web, query a database, hit an API — and then use the result in its answer.

🔍 Example

You ask “what's the weather in Boston?” The model can't know that. With tools, it outputs get_weather("Boston"), your app runs it, feeds back “72°F,” and the model replies in plain language.

Tool use is the bridge from “a model that talks” to “a model that does things” — which sets up agents.

Reasoning models

Reasoning models are trained to “think before they answer” — generating a hidden chain of intermediate steps, checking their own work, then giving you the final result. They're noticeably better at math, logic, multi-step planning, and hard debugging.

If your task is a quick lookup, rename, or simple snippet…
→
Then a fast standard model is cheaper and plenty good.
If the task needs planning across many steps or careful logic (a tricky bug, a system design)…
→
Then switch to a reasoning model and accept it's a bit slower.

Agents 🤖

An agent is a model put in a loop with tools and a goal. Instead of answering once, it plans, takes an action, looks at the result, and decides the next action — repeating until the goal is met. This is the shift that defined 2024–2025 (see the Timeline).

🔍 Example

A coding agent given “add dark mode” will read your files, edit the CSS and a toggle, run the app, notice a contrast bug, fix it, and re-run — all before handing it back to you. You gave a goal, not step-by-step instructions.

⚠️ Watch out

More autonomy = more ways to go wrong. Agents can take real actions (edit files, run commands, spend money), so keep a human in the loop, work in version control, and review what they did before you ship it.

Check your knowledgeWhat's the key difference between plain “tool use” and an agent?

Tool use lets a model take one action. An agent puts that in a loop with a goal: think → act → observe → repeat. That autonomy is powerful, which is exactly why you keep a human reviewing the result.

Prompting vs RAG vs fine-tuning — which do I need?

A question that trips up almost everyone. Here's the honest order to try things in:

If the model just needs clearer instructions or better wording…
→
Then improve the prompt. Free, instant, solves most problems. Start here.
If it needs facts it doesn't have — your docs, your code, recent info…
→
Then use RAG. Give it the source material at question time.
If it needs a consistent style, format, or behavior that prompting can't reliably enforce…
→
Then consider fine-tuning. Most powerful, most effort — a last resort, not a first move.
✅ Tip

Rule of thumb: prompt first, RAG for knowledge, fine-tune for behavior. 90% of everyday needs never get past the first two.
