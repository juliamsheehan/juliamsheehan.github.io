🧰 Tools & Workflows

Specific products come and go, but the categories are stable. Learn the categories and you can slot any new tool into the right box in seconds. Examples below are illustrative, not endorsements — check what your workplace approves.

The categories of AI coding tools

💬

Chat assistants (web)

A browser chat you paste into. Great for questions, explanations, and snippets — separate from your editor.

e.g. Claude, ChatGPT, Gemini.

⌨️

IDE assistants

Live inside your editor: autocomplete, inline edit, and a chat sidebar that can see your open files.

e.g. GitHub Copilot, Cursor, Windsurf, JetBrains AI.

🤖

Agentic / CLI coding tools

You give a goal; the agent reads the repo, edits many files, runs commands and tests, and iterates. Often run in the terminal.

e.g. Claude Code, Cursor agent, Codex/Copilot agents, Aider.

🔍

Code review & PR bots

Attach to your repo and comment on pull requests — flagging bugs, style, and security before a human looks.

e.g. GitHub/GitLab review bots, CodeRabbit-style tools.

🧩

API & SDKs (build your own)

Call the model from your own code to build features — a chatbot, a classifier, a RAG search. This is where tokens, temperature, and function calling from Fundamentals become knobs you set.

e.g. the Anthropic, OpenAI, and Google model APIs.

💻

Local / on-device

Run an open-weight model on your own machine — private and offline, at the cost of some capability and setup.

e.g. Ollama, LM Studio running Llama / Mistral / Qwen.

Which should I start with?

If you're just getting comfortable and want zero setup…
→
Then start with a web chat assistant. Ask it to explain code and draft snippets.
If you code in an editor daily and want a speed boost…
→
Then add an IDE assistant for autocomplete + inline edits where you already work.
If you're ready to hand off whole tasks and review the result…
→
Then try an agentic/CLI tool on a personal project first, working in git.
If privacy or offline use is non-negotiable…
→
Then run a local model — smaller, but nothing leaves your machine.
✅ Tip

You don't have to commit to one. A common, healthy setup is web chat for thinking + IDE assistant for typing + an agent for the big lifts — whichever your workplace allows.

What is MCP?

MCP (Model Context Protocol) is a shared standard for connecting AI tools to your data and other software. Before it, every assistant needed a custom, one-off integration for each service (your files, GitHub, a database, Slack…). MCP makes those connections plug-and-play.

💡 In plain English

MCP is the “USB-C port” for AI. Build one MCP connector for a tool, and any MCP-aware assistant can use it — no bespoke wiring per assistant.

🔍 Example

Add a “GitHub” MCP server to your coding agent and it can now read issues and open pull requests directly — the same server would work with a different assistant tomorrow.

Workflow patterns that keep quality high

Tools give you speed; patterns keep that speed from creating a mess. Four that hold up:

1 · Plan → approve → build

For anything non-trivial, ask for a plan first. Read it, correct wrong assumptions, then let it write code. Catching a bad approach in a 5-line plan is far cheaper than in 300 lines of code.

2 · Small, reviewable steps

Prefer many small changes over one giant one. Each step: generate → read → run/test → commit. If something breaks, you know exactly which step did it and can undo cleanly.

3 · Spec-first (write the “what” down)

Put the requirements and constraints in a short doc (or the prompt) before generating. A clear spec is the context the model needs — and doubles as your acceptance checklist.

4 · The review gate

Nothing merges without a human read and passing tests — even (especially) agent output. Optionally add a review bot as a first pass, but the human gate stays.

⚠️ Watch out

The failure mode isn't “AI writes bad code” — it's “AI writes a lot of code fast and nobody reads it.” These patterns exist to keep a human in the loop at the speed the tools now move.
